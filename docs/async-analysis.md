# Асинхронність у html2md-clean — аналіз та рекомендації

> Коротка відповідь: **переносити ядро на `async` НЕ потрібно і не варто.**
> Бібліотека — суто **CPU-bound** (парсинг HTML + regex), без мережевого чи
> файлового вводу-виводу всередині конвертації. Наявного асинхронного
> «обгортання» через `asyncio.to_thread` (`generate_markdown_async`) достатньо,
> і воно **працює коректно** в async-контексті. Нижче — повний розбір чому.

---

## 1. Що взагалі дає `async` у Python

`async/await` прискорює **тільки I/O-bound** навантаження: коли код багато часу
**чекає** (мережа, диск, БД, сокети) і в цей час event loop може виконувати інші
задачі. Для **CPU-bound** роботи (обчислення, парсинг, regex) `async` **не дає
паралелізму** — через GIL один потік однаково рахує послідовно, а сам `await`
лише додає накладні витрати на перемикання корутин.

Правило:
- **I/O-bound** → `async` (або треди) допомагає.
- **CPU-bound** → потрібні **треди для non-blocking** і **процеси для
  справжнього паралелізму** (обхід GIL), а не корутини.

---

## 2. Якою є ця бібліотека за природою

Уся робота конвертації — це CPU:

| Етап | Що робить | Тип | Мережа/диск? |
|------|-----------|-----|--------------|
| `SelectolaxParser` / `BeautifulSoup` | парсинг HTML у дерево | CPU | ні |
| `UnifiedMarkdownConverter.convert` | обхід дерева, генерація Markdown | CPU | ні |
| regex-заміни (inline, noise patterns) | `re.sub` по рядку | CPU | ні |
| `_remove_noise_*` | обхід і `decompose()` вузлів | CPU | ні |
| `htmldate.find_date` (опц.) | парсинг дат **із вже переданого HTML** | CPU | ні |
| `trafilatura.extract` (опц.) | вилучення основного контенту з HTML | CPU | ні |
| `courlan.clean_url` (опц.) | нормалізація URL-рядка | CPU | ні |
| `nh3.clean` / `ftfy.fix_text` (опц.) | санітизація/mojibake | CPU | ні |

**Ключовий момент:** усі бібліотеки-помічники (`trafilatura`, `htmldate`,
`courlan`) приймають **готовий HTML-рядок** і нічого не завантажують із мережі.
Тобто всередині пайплайну **немає жодного `await`-придатного I/O**. Єдиний I/O у
проєкті — читання файлу/stdin у CLI (`main_service.py`), і це поза ядром.

Висновок: **переписувати `convert`/`generate_from_html` на `async def` немає що** —
там нема на чому чекати. Це була б «фейкова» асинхронність (`async` без жодного
`await` на I/O), яка лише ускладнює код і сповільнює його.

---

## 3. Що вже є і чому це правильний підхід

У `markdown/generator.py` є:

```python
async def generate_markdown_async(html: str, options=None) -> MarkdownResult:
    generator = MarkdownGenerator(options)
    return await asyncio.to_thread(generator.generate_from_html, html)
```

Це **канонічний і правильний** спосіб інтегрувати CPU-bound синхронну функцію в
async-застосунок:

- `asyncio.to_thread(...)` виносить важку синхронну роботу в **пул потоків**, тож
  **event loop не блокується** — інші корутини (HTTP-хендлери, таймери) далі
  крутяться.
- Для парсерів це працює навіть попри GIL, бо `lxml`/`selectolax` — це
  C-розширення, які на час важкого парсингу **відпускають GIL**. Отже кілька
  паралельних `to_thread`-конвертацій можуть реально виконуватись частково
  паралельно.
- Є коректний fallback на `loop.run_in_executor` для середовищ без
  `asyncio.to_thread`.

Тобто **у FastAPI/aiohttp це вже нормально працює** і не «підвішує» сервер.

---

## 4. Чи «нормально працює відповідь/writing у асинхроні»

Так. Функція повертає той самий `MarkdownResult`, що й синхронний шлях (жодної
різниці в даних чи розмітці) — просто через `await`. Ніякого стану, що ділиться
між викликами, немає: кожен виклик створює свій `MarkdownGenerator`/
`UnifiedMarkdownConverter`, тому виклики **безпечні для конкурентного
використання** і не заважають один одному.

Один нюанс про запис (writing) результату: якщо після конвертації ви **пишете
файл**, то у async-коді робіть це асинхронно (напр. `aiofiles`) або теж через
`to_thread`, щоб не блокувати loop на диску. Сам рядок Markdown у пам'яті —
готовий одразу.

---

## 5. Коли асинхронність тут дійсно корисна (і коли ні)

**Корисна, якщо ви:**
- обробляєте HTML **у веб-сервісі** (FastAPI/Starlette/aiohttp) і не хочете, щоб
  важка конвертація блокувала обробку інших запитів → використовуйте
  `generate_markdown_async` (вже є);
- **завантажуєте сторінки з мережі**, а потім конвертуєте: мережа — то I/O, її
  робіть `async` (httpx/aiohttp), а конвертацію лишайте в `to_thread`.

**НЕ корисна, якщо ви:**
- маєте простий CLI/скрипт, що конвертує один файл — синхронний виклик
  найпростіший і найшвидший;
- хочете «прискорити» саму конвертацію одного документа — `async` цього не
  зробить (CPU-bound). Тут допомагає лише швидший парсер (selectolax vs bs4) або
  паралелізм по процесах.

---

## 6. Масштабування CPU-bound роботи (правильні інструменти)

Якщо треба обробити **багато документів швидше**, вибір залежить від мети:

| Мета | Інструмент | Чому |
|------|-----------|------|
| Не блокувати event loop у сервері | `asyncio.to_thread` (вже є) | GIL відпускається C-парсером, loop вільний |
| Багато документів конкурентно в async | `asyncio.gather(*[generate_markdown_async(h) for h in htmls])` | розкладає роботу по треди-пулу |
| **Справжній паралелізм** на всіх ядрах | `concurrent.futures.ProcessPoolExecutor` | обходить GIL, кожен процес — окреме ядро |
| Батч у синхронному коді | `ThreadPoolExecutor` (map) | простий паралелізм для C-парсерів |

Приклад конкурентного батчу в async без зміни ядра:

```python
import asyncio
from markdown.generator import generate_markdown_async

async def convert_many(htmls: list[str]) -> list:
    return await asyncio.gather(*(generate_markdown_async(h) for h in htmls))
```

Приклад справжнього паралелізму (CPU-важкий масовий обробіток):

```python
from concurrent.futures import ProcessPoolExecutor
from markdown.generator import MarkdownGenerator

def _work(html: str) -> str:
    return MarkdownGenerator().generate_from_html(html).fit_markdown

with ProcessPoolExecutor() as pool:
    results = list(pool.map(_work, htmls))
```

> Порада: для дуже великих обсягів комбінуйте — `async` для мережевого
> завантаження + `ProcessPoolExecutor` (через `loop.run_in_executor(pool, ...)`)
> для самої конвертації.

---

## 7. Обмеження й застереження

- **GIL:** чисто-Python ділянки (regex, обхід дерева адаптера) паралельно НЕ
  прискоряться в тредах — лише C-парсер. Для повного паралелізму — процеси.
- **Накладні витрати `to_thread`:** для дуже дрібних HTML (кілька тегів) виклик
  через тред дорожчий за просто синхронний виклик. У гарячому циклі з мікро-
  документами синхронний шлях може бути швидшим.
- **ProcessPool + pickle:** передавати варто **рядки HTML і рядки Markdown**, а
  не `MarkdownResult`/`BeautifulSoup`-обʼєкти (лишні витрати на серіалізацію).
- **Порядок:** `asyncio.gather` зберігає порядок результатів; при ручному
  `as_completed` — ні.

---

## 8. Підсумок і рекомендація

1. **Ядро лишаємо синхронним.** Конвертація — CPU-bound, `async def` для неї не
   має сенсу (нема I/O для `await`).
2. **Асинхронний доступ уже є** і зроблений правильно — `generate_markdown_async`
   через `asyncio.to_thread`. У async-серверах це працює коректно і не блокує
   event loop.
3. **Для масштабу**: конкурентність у async — `asyncio.gather` поверх наявної
   async-функції; справжній паралелізм — `ProcessPoolExecutor`.
4. **Що можна докрутити (опційно, не обовʼязково):**
   - додати `generate_markdown_async(source, ...)` overload для адаптерів (зараз
     лише для `html: str`);
   - зробити тонкий async-батч-хелпер `generate_many_async(htmls)` навколо
     `gather` для зручності;
   - у документації прямо показати рецепт «httpx (мережа, async) + to_thread
     (конвертація)».

**Тобто переносити на асинхрон не потрібно — достатньо наявної обгортки; вона
працює нормально.** Реальний виграш у швидкості дає не `async`, а вибір парсера
(selectolax) і паралелізм по процесах для масових обсягів.
